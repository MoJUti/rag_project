# 代码规范

本规范适用于项目后续新增和修改的代码。已有代码在相关功能变更时逐步整理，不单独进行大范围格式改写。

## 1. 清楚、简洁地实现功能

- 优先选择容易理解、容易验证的直接实现。简洁指逻辑清楚、没有不必要的步骤，不以代码行数少为目标。
- 避免重复遍历同一批数据、深层嵌套、过长函数和为了省行数而写的复杂表达式。可用提前返回、小函数和标准库简化逻辑。
- `for` 循环可以正常使用。逐条校验、分批处理、保留处理顺序或记录错误时，明确的循环通常更合适。
- 相同规则重复出现时再抽取共用代码；不为尚未出现的需求提前增加多层抽象。
- 一个函数承担一个清楚的职责。函数名和变量名用准确的英文表达用途；同一概念保持命名一致。

## 2. 注释和类型标注

- **所有代码注释和文档字符串使用中文。** 第三方接口要求的字段名、代码标识符和专有名词可保留原文。
- 注释解释设计原因、算法意图、外部限制和容易误改的边界；不逐行复述代码已经表达清楚的操作。行为改变时同步修改注释。
- 新增或修改的核心函数标注参数和返回值类型。接口、数据模型以及策略实现的输入输出必须明确；一眼能看懂的局部变量不强求标注。

## 3. 明确处理异常

- 失败时明确指出**哪一步、哪个对象、为什么失败**，例如文档解析失败、缓存向量维度与集合不符。不要把失败伪装成空结果或成功状态。
- 不使用裸 `except`，不无声吞掉异常。需要转换异常时保留原始原因；只捕获能够正确处理的异常。
- 对超时、限流等可恢复故障设置有上限的重试；输入不合法、数据损坏、版本或维度不匹配等问题直接报错。
- 日志提供定位所需的标识和阶段，不输出密钥等敏感信息。

## 4. 测试核心行为

- 改动解析、切块、向量写入、召回、融合、重排等核心逻辑时，增加或更新相应测试，并运行受影响的测试。
- 测试覆盖正常结果以及关键边界和失败路径。修复缺陷时增加能复现该缺陷的回归测试。
- 测试验证外部可观察的行为与结果，避免照着函数内部实现重复写一遍；外部 API 可使用替身，关键集成路径再使用真实服务验证。
- 测试失败必须说明原因，不能为了让测试通过而跳过关键断言。

## 5. 保持改动聚焦

- 功能改动只修改相关代码；不要顺手大范围重排格式或重构无关模块。
- 新代码遵循项目已有格式和目录约定。格式化工具可统一处理机械格式，但不能替代对逻辑、命名、异常和测试质量的检查。
