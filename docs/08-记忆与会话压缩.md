# 节点8：记忆与会话压缩

状态：当前范围的实现与定点验证完成，待用户确认本轮收尾；32K/4K默认，摘要遗忘回归通过，可选历史消歧接线及8场景对照完成。原问题检索仍默认，跨会话记忆关闭；更广多轮场景未声称全验收。

## 1. 目标与边界

让多轮对话能理解“它、刚才那份、继续比较”等指代，在上下文有限时保留重要条件，同时避免不同会话串信息。记忆只帮助理解问题和用户明确表达的偏好，不把历史模型回答升级为知识库事实，也不复用旧回答的引用编号。

本节点不接入节点7被用户暂缓的草稿校验，不将记忆压缩当作表格读数错误的修复。

## 2. 现有实现与已复现问题

`memory/history_store.py` 当前将压缩后的消息写回同一个历史文件。配置为保留最近3轮、累计5轮触发摘要，摘要模型为旧的 `qwen-turbo` 初始化路径；初始化/摘要失败时有宽泛捕获与截断回退。

本轮用替身摘要器在内存逐轮模拟7轮，每次按照真实写入逻辑，将上次压缩结果与新一轮合并：

| 已提交轮数 | 压缩后保留普通轮数 | 累计摘要调用 |
|---|---:|---:|
| 1、2、3 | 1、2、3 | 0 |
| 4、5、6、7 | 每次均为3 | 0 |

原因是第4轮已经先裁到3轮，后续每次追加后只有4轮，始终达不到5轮触发门槛。现有一次性传入8轮的单元测试能触发摘要，但没有覆盖真实逐轮追加路径。

这是对当前默认参数的可复现结果，不代表所有历史文件都已检查或旧信息都可恢复。复现实验没有写入或删除用户聊天文件，也没有请求真实模型。

此外：

- 原始历史与模型上下文混在一起，压缩会影响历史回放和再次提取。
- `len(text)//2`只是粗略估算，不能保证实际Token不超限；现有预算裁剪允许最后一轮仍超预算。
- 摘要失败后简单截断文本，会隐藏失败并可能丢掉重要条件；应明确记录降级状态。
- 聊天模型临时改用GLM，不代表旧摘要器已同步改用GLM或其接口已验证。

## 3. 建议的职责划分（待确认）

1. 完整历史存档：保存用户和助手原始消息，不因压缩而覆盖；继续保留显式清空/删除能力，不把“完整保存”当作禁止用户删除。
2. 上下文组装：从完整历史构建“近期原文＋较早摘要”，每次有明确预算；压缩只是生成一个视图，不删除历史。
3. 摘要状态：记录覆盖到哪条消息、生成版本、失败/降级原因；已覆盖内容不重复摘要，更新事实保留新旧关系。
4. 记忆接口：区分会话内上下文与跨会话长期记忆。跨会话只保存用户授权的偏好或事实，默认不共享其他会话全文。

不在此时决定换数据库、引入新框架、摘要模型或具体Token阈值。旧文件需要兼容读取或明确迁移策略，不自动覆盖。长期记忆与摘要都应支持查看、纠正和删除；存储接口可替换，先不扩展到多租户账户系统。

## 4. 评测优先于复杂策略

先建立少量中文多轮轨迹，记录每轮问题、允许记住的事实、应被更新/删除的内容、相关来源和预期行为：

- 连续逐轮追加是否丢失早期条件，摘要是否按预期触发。
- “它/刚才那份”是否正确指向对象，换话题后不误用旧条件。
- 数值、日期、否定条件、用户更正是否在压缩后保留。
- 不同会话隔离，历史伪指令不提升权限，历史错答不当作资料事实。
- 摘要接口失败、历史损坏、超长单轮时明确报错或标记降级。
- 原始历史可回放；用户删除后不从摘要或长期记忆中重新带回。

比较全历史参考、窗口与摘要组合时，分别报告事实保留/更新正确率、错误记忆、输入Token、压缩耗时及模型用量。替身测试只验证机制，真实模型测试才衡量摘要与回答表现；不从单条“能记住”宣称最优。

## 5. 实施前先确认

第一项选择是记忆范围：先完成当前会话内的连续对话，还是本节点就实现跨会话长期偏好记忆。建议先完成会话内，跨会话保留接口但不默认启用；待用户确认后，再讨论摘要模型、预算及持久化细节。

## 6. 已确认范围与第一阶段实现（2026-10-16）

用户确认：跨会话记忆暂不启用，摘要使用已配置GLM-5.3-flash、low思考档。不引入新框架或换数据库。初始沿用最近3轮、累计5轮、4000估算Token及1500摘要字符上限；2026-10-16用户确认切换为32K历史与4K摘要Token上限，见第10节。

### 完整历史与上下文分开

- `memory/file_history.py`：新版存档为 `chat_history/.memory_v2/<session_id>.json`。同一文件同时保存完整原始消息、摘要、覆盖游标及策略身份，避免原文和游标分别写入导致不一致。临时文件在同目录写完后原子替换。
- `get_history()` 为前端返回完整记录；`get_context_history()` 为回答链返回压缩视图，新增问答仍写入同一份完整存档。会话列表、清空和删除已兼容新旧格式。
- 旧 `chat_history/<session_id>` 文件只读兼容，首次新写入带上旧文件现存内容，原文件不覆盖。旧逻辑已丢失的早期对话不能凭空恢复。用户明确清空/删除时才清除对应旧文件和新版状态，避免旧摘要复活。
- 新版目录加入Git忽略规则，没有把用户现有聊天文件写入或迁移；本轮测试只使用临时目录和合成轨迹。

### 触发、增量与失败

`memory/session_context.py` 根据完整存档计轮数。触发前不先裁成3轮；达到门槛后，将较早轮次摘要，保留最近原文。记录已覆盖消息位置及内容指纹，后续只摘要新增的较早消息。模型、提示词或参数变化时从存档重建，不直接复用不匹配的状态。

摘要失败、空输出、过长输出明确记录 `degraded` 状态，不把简单截断冒充成功摘要；同批失败在重复读取时不重复付费请求，新增需要摘要的历史或显式重试时再尝试。降级状态目前可从日志和状态对象读取，界面展示留在节点9。

摘要关闭时只使用近期窗口，但完整存档不裁掉。最新一轮本身超过历史预算时明确报错，不静默截断；预算不足时可在模型视图中省略旧轮或摘要，并标记降级。历史预算只针对历史视图，不含新提问、系统提示和知识库证据，也不是GLM精确计费Token。优先用本地 `cl100k_base` 估算，缺失时按UTF-8字节保守估计。

摘要使用已确认的智谱适配器，不再调用旧千问摘要器；GLM保持low。提示词保留用户更正、否定条件及删除偏好，区分用户条件和助手说法。历史摘要在回答链仍作为普通上下文，不提升为系统指令或知识库事实。

## 10. 当前默认策略：32K / 4K（2026-10-16）

在完成[同题回答质量与耗时对照](节点8同题回答质量与耗时对照.md)后，用户明确选择32K / 4K作为当前配置：

- 历史模型视图上限为32768估算Token，其中包含摘要与保留的原文，不是额外再加4096。
- 摘要上限为4096估算Token，不要求写满；当前模式不再使用1500字符限制。
- 按Token预算触发摘要，预算内不按累计5轮提前压缩；超预算时预留摘要空间，尽量保留更多近期完整轮次。最近3轮和5轮参数仅用于兼容旧轮次模式，不限制当前正常Token策略的保留轮数。
- 完整原文存档不裁剪。切换策略会使旧上下文缓存指纹失效，下次读取时按新策略重新构建，必要时调用GLM摘要。
- 摘要继续使用已配置GLM、low档，跨会话记忆仍关闭，不改变回答模型池。

配置位于 `core/config.py`，已运行的应用需要重启后加载新默认值。本次只修改配置和验证，不额外调用付费模型，不自动启动或重启现有应用。这是用户选择的暂用方案，不宣称已证明最优。
