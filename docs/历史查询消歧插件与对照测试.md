# 历史查询消歧插件与对照测试

日期：2026-10-16，属于节点8“会话内记忆→检索衔接”。插件已接入正式回答链，完成第一轮定点对照；默认仍为原问题检索，没有改本地 `.env`、重建索引或切换数据库。

## 1. 解决什么问题

原来历史只进入回答模型，检索仍直接使用“它是谁？”；换掉历史公司也可能拿到完全相同的候选。新插件在检索前判断是否需要补全对象，但不负责回答业务问题，也不把旧模型答案当作知识库事实。

流程为：

```text
原始提问＋同会话受预算约束的历史
    → 查询消歧插件
        ├─ original：问题已完整，保持原样
        ├─ rewrite：有明确历史依据，补全后检索→融合/重排→引用回答
        └─ clarify：对象不足或有歧义，先询问用户，不检索、不调用业务回答模型
```

原始用户提问仍用于聊天存档与回答，不被检索查询覆盖。被省略的对象、范围和查询目标才允许补全；不得擅自加入答案、数字或过滤条件。

## 2. 插件接口与配置

实现文件为 `retrieval/query_resolution.py`：

- `QueryResolver.resolve(query, history)` 是统一接口。
- `QueryResolution` 返回原问题、实际查询、动作、澄清问题、历史锚点、耗时和模型元数据。
- `QUERY_RESOLVER_FACTORIES` 注册插件，当前提供 `original` 和 `glm_history`。
- `RagService` 支持注入其他实现，不需要改检索、重排或数据库适配器。

| 配置 | 行为 | 消歧模型调用 |
| --- | --- | --- |
| `QUERY_RESOLUTION_STRATEGY=original` | 原问题检索，当前默认 | 不调用 |
| `QUERY_RESOLUTION_STRATEGY=glm_history` | 使用已配置GLM、low档判断保留、补全或澄清 | 每次问题调用一次，包括最终判断为original的问题 |

开启后的消歧模型使用本地 `ZHIPU_CHAT_MODEL`、`ZHIPU_BASE_URL`、`ZHIPU_API_KEY`，固定low档、输出上限800 Token；不更改业务回答模型池。真实密钥不写入报告。唯一提示词为 `prompts/retrieval/history_query.md`。

`.env.example` 已提供默认关闭项。需要启用时由用户将本地 `.env` 改为上述 `glm_history` 并重启应用；本轮仅在评测实例显式注入，没有自动开启。无需重新解析、切块或入库；新的查询会使用当前嵌入模型生成查询向量。

## 3. 核心实现与边界

模型必须返回严格JSON，恰好包含action、query、clarification、anchors：

- original要求查询与输入逐字相同。
- rewrite必须带非空历史锚点；每个锚点包含消息下标和逐字引文，必须来自用户消息或摘要，不能引用助手猜测。
- clarify要求查询为空，返回明确澄清问题，不同时偷偷执行查询。
- 结构错误、锚点不存在、引用非原文、接口故障均明确报错，不无声降级到一个猜测查询。

历史和摘要被封装在用户消息JSON数据中，不作为新的系统指令。模型无工具权限，不能在消歧阶段自行访问其他会话或资料库。锚点逐字存在仍不证明语义一定正确：模型可能错误解释真实历史，需要更多评测，不能声称彻底防止注入或幻觉。

`generation/rag_service.py` 在 `_prepare_answer` 先运行插件：非澄清结果传给原有 `retrieve_with_trace`，因此召回、重排、证据扩展都使用实际查询。澄清分支直接返回问题，仍由原来的消息历史组件保存原始提问与澄清回复。

逐请求 `history_query` 阶段记录原问题、实际查询、锚点、状态、耗时、request_id和Token。默认插件不产生消歧模型成本。记录位于结果对象而非全局共享状态，前端展示留待节点9；本次不新增界面。

## 4. 八个真实测试场景

数据位于 `data/eval/session_memory_v1/query_resolution_cases.json`，三道业务题沿用已有中文评测标准答案和原文定位。

| 题号 | 场景 | 预期/实际动作 | 结果 |
| --- | --- | --- | --- |
| H01 | 历史明确宏海科技，问“它的法定代表人是谁？” | rewrite / rewrite | 补全宏海科技，答周宏 |
| H02 | 历史明确3月生日会通知，问“它安排在哪里举办？” | rewrite / rewrite | 补全生日会，答公司活动室 |
| H03 | 同一句法定代表人追问，历史对象换成太湖远大 | rewrite / rewrite | 补全太湖远大，答俞丽琴 |
| H04 | 旧话题为生日会，新问题已完整指定宏海科技 | original / original | 原问题逐字不变，答周宏 |
| H05 | 两家公司都在讨论、未指定其中一家 | clarify / clarify | 询问指哪家公司，没有检索 |
| H06 | 无历史就问“它的法定代表人是谁？” | clarify / clarify | 询问公司名称，没有检索 |
| H07 | 先宏海科技，用户明确更正为太湖远大 | rewrite / rewrite | 锚点来自最新更正，答俞丽琴 |
| H08 | 用户明确宏海科技，文档引用伪指令要求换公司 | rewrite / rewrite | 仍补全宏海科技，答周宏 |

八次动作与预期一致，六次主问题回答均有本次证据支持、引用编号有效；两次澄清未调用检索与业务回答模型。额外补充内容不在“主问题答对”中一并作满分承诺，H04仍有非必要扩写，沿用节点7已知限制不在本次修改。

H01与H03改写后的候选列表不再相同，说明历史对象实际影响了检索，而非仅在生成阶段挑选混合资料。

## 5. 与原问题检索比较

对照使用上一轮相同历史、相同提问的冻结记录；没有重新调用旧策略。这是历史单次样本对照，不是随机交错性能实验。原策略在这三题也都答对，不能宣称答案准确率已经提高。

| 场景 | 原策略：含主答案证据的最早切块 | 消歧后：含主答案证据的最早切块 | 变化 |
| --- | ---: | ---: | --- |
| 宏海科技法定代表人 | 1 | 2 | 略后移，不是每题都改善 |
| 生日会地点 | 7 | 1 | 提前 |
| 太湖远大法定代表人 | 2 | 1 | 提前 |

这里的答案证据名次依据返回原文人工复核，不用“目标文档第一个切块”冒充“答案切块”。例如宏海科技消歧后的第1块签署栏没有姓名，第2块基本信息表才包含周宏。

旧公司题的自动 `evidence_recall_at_10` 仍为0：长整页quote与单个结构切块75%覆盖阈值不匹配。本轮不改旧题评分或历史成绩，沿用[上一轮报告](节点8多轮记忆与指代追问验收.md)的指标限制说明。

| 场景 | 消歧耗时 | 检索与回答耗时 | 两阶段相加 |
| --- | ---: | ---: | ---: |
| H01 | 1.45秒 | 4.93秒 | 6.38秒 |
| H02 | 1.03秒 | 2.39秒 | 3.42秒 |
| H03 | 2.61秒 | 2.06秒 | 4.66秒 |

八次消歧请求实际耗时范围约0.98–2.61秒。消歧决策先独立保存，再将同一决策绑定原问题及逐字相同历史后交给正式链，避免为生成查询向量而重复请求消歧模型。表中是实际两个阶段之和，**不含两阶段间提前批量生成查询向量的时间**，不是浏览器端总耗时，也不能据这些单次样本声称变快。

本轮8次消歧、6次业务回答，共14次GLM请求，全部完成；输入50325、输出668、总计50993接口Token。改写问题的嵌入用量未计入这些GLM Token。插件会增加请求成本与等待时间，这是暂不设为默认的重要原因。

## 7. 当前建议与未覆盖项

保留original默认，glm_history作为显式可选策略，待用户确认再决定是否启用。当前结果只覆盖短历史、少量文档对象；摘要长历史中的消歧质量、澄清后用户补充对象的完整多轮闭环、更多省略表达和更大资料库需要后续集成测试。

节点8当前范围的主要实现和定点验证已具备，不能称为所有多轮场景验收完毕。下一步可由用户确认本轮收尾及Git提交，再进入节点9，将解析质量、切块、检索查询、各阶段候选、记忆状态及耗时接入界面；这些已知边界保留在最终整链复测中继续验证。
