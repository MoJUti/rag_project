TECHNICAL EVOLUTION PLAN · V0.1

现代知识库系统演进方案

从已经跑通的 RAG MVP 出发，建立评测、可观测和可替换的技术基座，再用实验决定每一次升级。

本方案不把现有项目推倒重来。现有 Streamlit、Chroma、BM25、RRF 和会话摘要继续作为可运行基线；后续解析、切块、检索、生成和记忆能力均通过接口并行接入，并由统一评测集决定是否替换。

已有 MVP评测先行全链路可观测渐进式重构可回退
起点现有系统持续可运行
主线基线 → 评测 → 实验 → 决策
目标多格式、混合检索、可解释
原则无证据，不替换
编制日期：2026-09-24状态：方案讨论稿 · 当前阶段不修改业务代码
01

执行摘要

项目已经越过“能否跑通”的阶段，下一步应从功能堆叠转向可度量演进。

核心路线

保留现有 MVP 作为 baseline，先建立稳定标识、评测数据和全链路追踪，再逐层引入现代文档解析、结构化切块、原生混合检索、Rerank、多模态和长期记忆。任何替换都必须通过同一隐藏测试集。

1 个基线现有系统冻结为对照组
8 个阶段每阶段都有验收门
3 类数据金标、合成、真实回流
0 次盲换技术选择必须有证据

与传统 MVP 开发的区别

过去：0 → 1

验证链路可行

上传文本、切块、入库、召回、生成、显示答案。现有项目已经完成这一目标。

现在：1 → 可验证演进

验证系统是否真正更好

需要可重复的数据集、指标、追踪、版本和决策记录，避免“重构完成但无法判断收益”。

02

现状与演进原则

现有代码是资产，也是第一条可重复的实验基线。

层级当前实现状态判断下一步
界面Streamlit 上传与对话可运行基线短期保留；Studio 成熟后再决定是否迁移 React/Next.js。
文档处理面向法律文本的预处理和条文切块领域专用抽象统一文档模型，增加 Docling/MinerU 适配器。
向量检索本地 Chroma继续保留作为 baseline，与新版 Chroma 原生 Hybrid、Qdrant 并行评测。
关键词检索Python 内存字符级 BM25优先改进改为持久化 sparse/BM25，统一过滤、版本与追踪。
融合应用层手写 RRF可作为对照增加 Weighted RRF、DBSF、Rerank 实验。
记忆会话摘要压缩能力有限演进为原始历史、工作、语义、情节和程序记忆。
评测与追踪缺少统一评测集和阶段级 trace首要缺口在更换核心组件前补齐。

五条不可破坏的原则

P-01

Baseline 永远可运行

新链路失败时可以切回旧链路，并可以重放同一评测。

P-02

原始资料不可丢

原文件、解析结果、切块和索引分层保存；派生数据可重建。

P-03

稳定证据 ID

评测绑定证据单元而不是某一版 chunk ID，允许安全更换切块算法。

P-04

接口隔离供应商

Parser、Chunker、Embedding、VectorStore、Reranker、Generator 全部可替换。

P-05

先证明，再默认

最新技术进入候选池；只有通过本地评测，才进入默认路径。

P-06

每次运行可复现

记录模型、提示词、数据版本、索引快照、参数、代码提交和随机种子。

03

目标架构

业务体验、知识处理、检索实验和评测观察分层，避免未来再次把所有逻辑绑在 Streamlit 页面中。

架构边界

Vector DB 不保存全部业务真相。原始文件进入对象存储，文档版本、权限和任务状态进入 PostgreSQL；向量数据库只保存面向检索的派生表示，并可随时重建。

04

关键阶段节点

阶段按依赖顺序推进，不强行按日历排期。每个节点都产生可查看的成果和明确的继续条件。

M0
BASELINE

冻结现有 MVP 基线

记录当前代码提交、依赖、配置、测试文档、典型问题、输出、延迟和成本。修复阻止复现的问题，但不优化算法。

出口条件同一环境可重复启动；固定问题可重复运行；结果和 trace 可保存。
M1
EVAL CORE

建立最小评测闭环

先做一批人工金标问题，覆盖事实、精确词、多跳、无答案、表格和多轮追问；建立 stable evidence unit。

出口条件一条命令运行 baseline；生成召回、答案、引用、延迟和成本报告。
M2
INGESTION

统一文档模型与多格式入口

保存原文件，引入 Parser 接口；并行测试 Docling 与 MinerU；统一标题、段落、表格、图片、公式、页码和坐标。

出口条件选定格式可入库；解析结果可视；失败可重试；所有派生数据可重建。
M3
CHUNK LAB

建立切块实验室

实现结构切块、Parent–Child、Sentence Window；Semantic/Late Chunking 作为候选。评测绑定证据单元而非 chunk ID。

出口条件至少三种策略可并行运行；切块边界和父子关系可视化；有分项评测。
M4
RETRIEVAL

检索锦标赛与数据库决策

对比当前 Chroma + 内存 BM25、新版 Chroma Hybrid、Qdrant Hybrid；随后增加 Reranker 和多向量候选。

出口条件完成隐藏集对比；形成 Chroma/Qdrant ADR；迁移必须有可量化收益。
M5
ANSWER

上下文构建、回答与引用

引入去重、父块恢复、Token 预算、证据充分性检查、拒答和 Claim → Evidence 引用校验；生成模型保持可插拔。

出口条件回答可追溯到页/块；支持无答案；生成质量不掩盖召回问题。
M6
RAG STUDIO

全流程可视化工作台

展示解析页面、文档树、切块、各路召回、融合、重排、上下文、答案引用、实验差异和回归。

出口条件无需查看日志即可定位一次错误发生在哪一阶段。
M7
MEMORY

分层记忆与会话压缩

在原始历史之上增加工作、语义、情节和程序记忆；记录来源、时间、置信度、冲突和删除状态。

出口条件通过更新、冲突、时序、遗忘、跨会话和摘要失真测试。
M8
HARDENING

平台化和生产加固

补齐租户、权限、队列、限流、备份、数据生命周期、安全、成本预算和回滚；再决定替换 Streamlit。

出口条件达到约定 SLO；灾备演练通过；版本升级和回滚流程明确。

关键依赖

M1 是全路线的真正起点

没有 M1 的评测闭环，M2—M8 的“优化”都无法被可靠验证。可视化的 trace 骨架也应在早期建立，不应等前端阶段才补。

05

检索与数据库决策

Chroma 是否替换为 Qdrant 被纳入正式决策门；当前不预设替换结果。

候选实验矩阵

编号检索链路目的成熟度
R0当前 Chroma Dense + Python 字符 BM25 + RRF冻结原始表现Baseline
R1新版 Chroma 原生 Dense + Sparse + RRF评估不换数据库能否消除内存 BM25Candidate
R2Qdrant Dense + Sparse + Weighted RRF/DBSF统一索引、过滤与融合Candidate
R3R1/R2 + Text Reranker验证两阶段召回排序Candidate
R4Qdrant Hybrid + ColBERT/MultiVector学习 Late Interaction 并验证收益Experimental
R5Hybrid + Query Rewrite/Decompose + Sufficiency Check处理模糊、多跳和召回不足Experimental
R6Graph Retrieval只针对跨文档关系和多跳问题按需启用

Qdrant 替换门槛

GO

满足以下条件才迁移

在关键 query slice 上显著提升；统一 Sparse/Dense 后消除一致性问题；多向量或服务化确有需求；额外延迟、资源和运维成本可接受。

NO-GO

以下情况继续使用 Chroma

新版 Chroma 已满足需求；Qdrant 准确率无显著收益；数据规模小且单机为主；多向量只增加复杂度；团队暂不希望维护独立服务。

决策记录 ADR

输出数据版本、模型、参数、Recall@k、MRR、nDCG、端到端正确率、P50/P95、索引体积、峰值内存、部署与备份复杂度，以及最终选择和回退方案。

06

评测体系

评测不是最后验收，而是系统的控制平面；每个阶段都拥有自己的指标和失败样本。

数据集组成

GOLD

人工金标

真实文档、稳定证据单元、参考答案、必需与禁止 Claim、是否可回答；双人标注并裁决。

SYNTHETIC

合成覆盖

按 persona、难度、答案类型、单跳/多跳和格式扩充；必须抽样人工校验。

LIVE

真实回流

线上问题脱敏、聚类、标注后进入回归集；负责发现实验室未覆盖的失败模式。

分层指标

层级核心指标主要回答的问题
解析文字、阅读顺序、层级、表格、公式、页码坐标知识是否在入库前已经丢失或错位？
切块证据包含率、边界质量、重复率、父块恢复率证据能否被独立找到，又能恢复完整上下文？
召回Recall@k、MRR、nDCG、全证据召回率正确证据有没有进入候选集，排名在哪里？
生成Claim 正确性、Faithfulness、引用精确率/召回率、拒答模型是否只根据证据回答并正确标注出处？
端到端任务成功率、人工偏好、延迟、Token、成本用户是否真正获得有用结果？
记忆保留、更新、时序、冲突、遗忘、隐私删除、摘要失真跨会话是否记得该记的，同时忘掉该忘的？

评测有效性门槛

  • 按文档或来源划分开发集与隐藏测试集，防止同源泄漏。
  • LLM Judge 只做自动辅助，必须在人工标注样本上校准；回答模型与 Judge 尽量隔离。
  • 报告置信区间和问题类型切片，不能只比较一个平均分。
  • 加入同义改写、噪声、无答案、提示注入和文档版本变化等扰动测试。
  • 评测集需要能区分候选系统；所有方案都接近满分时，应提高难度而不是宣布成功。
07

全流程可视化

目标不是简单增加一个 Dashboard，而是让一次答案能够从结果反向追溯到原始文件和每个算法决策。

INGESTION VIEW

文档处理视图

原页面与解析树并排；展示 OCR、标题、表格、图片、坐标、警告、解析器版本和耗时。

CHUNK VIEW

切块实验视图

显示 chunk 边界、Token、父子、前后文、metadata、证据 ID 和不同策略差异。

QUERY TRACE

查询追踪视图

查询分类、改写、各路候选与分数、融合、Rerank、上下文打包、答案 Claim 和引用。

EXPERIMENT

实验与回归视图

并排比较两次实验；突出提升、退化、失败样本、成本、延迟和受影响 query slice。

MEMORY

记忆时间线

查看写入、更新、冲突、失效、召回和被压缩的记忆，并可回到原始消息。

OPERATIONS

运行与数据质量

任务队列、索引状态、失败重试、版本分布、解析质量、资源、Token 和预算。

实现边界

追踪数据采用 OpenTelemetry/OpenInference 语义，后端可先接 Phoenix 或 Langfuse；业务专属的文档、切块和证据视图由自己的 RAG Studio 提供。这样既利用成熟工具，又不把核心数据模型绑定到某一家平台。

08

记忆与会话压缩

记忆作为独立子系统建设；不再用一段不可追溯的滚动摘要替代全部历史。

层级内容存储与策略关键测试
原始历史消息、工具调用、检索结果不可由摘要覆盖；支持权限、保留期和删除完整性、删除传播
工作记忆最近消息、当前目标、未完成事项结构化状态 + 最近原文窗口任务连续性、指代
语义记忆稳定事实、偏好、身份和约束来源、时间、置信度、TTL、版本更新、冲突、过期
情节记忆任务、决定、行动和结果事件摘要链接原始 trace跨会话、多跳、时序
程序记忆工作规则、工具习惯、响应方式显式规则与可审计版本一致性、越权和错误固化

压缩流程

保留最近原文

高保真短窗口用于当前推理，不先压缩最近关键消息。

提取结构化状态

单独保存目标、决定、约束、实体、时间和开放问题，而不是只写自然语言摘要。

分层情节摘要

较旧会话形成可合并摘要，但每条摘要保留原消息 ID 和时间范围。

按需取回

依据查询使用 Dense、Sparse、实体和时间信号召回“足够的记忆”，而不是塞入全部历史。

实施顺序

记忆依赖稳定 trace、数据版本和评测框架，因此放在 M7。可以提前设计数据结构，但不应在召回和评测尚未稳定时大规模实现。

09

交付、边界与风险

每阶段交付可运行增量，控制重构范围，并保留旧路径直到新路径通过验收。

每个阶段的标准交付件

CODE

可运行实现

接口、适配器、迁移和回退开关。

DATA

版本化数据

样本、索引配置、运行产物和来源。

EVIDENCE

实验报告

指标、切片、失败案例、成本和结论。

DECISION

ADR

接受、继续实验或拒绝，以及触发重评条件。

主要风险与控制

风险典型表现控制方式
技术追新组件频繁更换，结果没有可比性技术雷达分 Production/Candidate/Experimental；默认链路保持稳定。
一次性重构长时间不可运行，错误来源不明旁路适配器、Feature Flag、双写/重放、逐阶段验收。
评测污染调参过度拟合少量公开题文档级隔离、隐藏测试、真实回流、统计置信区间。
解析静默错误回答错误被误判成模型问题解析独立指标、原文对照和坐标级引用。
记忆污染错误事实被长期保存并反复使用候选记忆验证、冲突检测、来源、TTL、撤销和删除测试。
成本失控多阶段、多向量、Judge 导致调用激增逐阶段预算、离线缓存、按 query 路由、高成本能力默认非全量启用。

当前明确不做

  • 不因为“更现代”立即删除 Chroma 或 Streamlit。
  • 不在没有评测集时引入 GraphRAG、Agentic RAG 或复杂多向量作为默认路径。
  • 不把向量数据库当作原始文档、权限和版本的唯一事实来源。
  • 不以单个公开榜单或厂商自报数字作为技术选择依据。

后续维护规则

技术条目记录名称、版本、发布日期、核验日期、官方来源、论文、许可证、成熟度、已知限制和本项目实验结果。最新技术只获得“进入候选池”的资格；通过隐藏测试集和运维评估后，才可能成为默认方案。

下一次讨论建议

先细化 M0 和 M1：确定现有 baseline 的冻结内容、第一批文档样本、问题分类、gold evidence 数据结构以及首版验收阈值。这会决定后面所有技术实验是否可信。
