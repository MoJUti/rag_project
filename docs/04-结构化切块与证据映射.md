# 节点 4：结构化切块与证据映射

## 1. 节点目标

本节点位于“统一解析结果”与“向量数据库/检索”之间。它只回答三个问题：

1. 解析后的标题、段落、表格、图片文字和公式怎样变成可检索的 chunk；
2. 每个 chunk 能否追溯回原文元素、页码、幻灯片、工作表或单元格范围；
3. 下一节点比较 Chroma 与 Qdrant 时，应固定使用哪套切块策略和参数。

本节点不修改 Streamlit，也不根据向量召回效果下最终结论。真正的 Recall@K、MRR、nDCG 和数据库性能属于节点 5。

## 2. 最终设计

### 2.1 统一 Chunk 模型

`KnowledgeChunk` 保存：

- 稳定的 `chunk_id`、`document_id` 和策略名；
- `text`、`token_count`、`chunk_type`；
- 标题路径 `section_path`；
- 原文元素 `element_ids`、原始位置 `source_locations`、附件 `asset_ids`；
- 完整切块参数和 `config_hash`。

因此，向量数据库只消费统一 Chunk，不直接依赖 MinerU、Markdown 或 Excel 的内部格式。相同文档、策略、序号和文本会生成相同 ID，便于重放和对比。

### 2.2 三种并行策略

| 策略 | 用途 | 当前定位 |
|---|---|---|
| `fixed_token_v1` | 全文按 Token 上限与 overlap 切分 | 无结构基线，用于判断复杂策略是否真的带来收益 |
| `structure_aware_v1` | 按标题、段落、表格、图片和公式切分 | 节点 5 默认方案 |
| `legal_article_v1` | 复用原有“第 X 条”法律条文切块 | 完整保留；检测到至少 3 个条文时可自动推荐 |

旧的 `ingestion/legal_chunker.py` 没有删除或改写，通过适配器接入统一接口。

### 2.3 结构感知规则

- 标题不单独丢入一个孤立块，而是作为标题路径附加到后续正文；
- 正文优先在段落和中文标点边界切分，超长连续文本再按 tokenizer 强制截断；
- 表格按行组织，重复表头，公式同时保留计算结果和公式表达式；
- 超宽表格允许进一步分片，所有输出仍受 `max_tokens` 硬上限约束；
- 图片说明与公式优先保持原子性，超过上限时才拆分；
- 每个结构块携带原解析元素和来源位置，后续可生成引用，也可供前端高亮原文。

Token 统计优先使用 `tiktoken/cl100k_base`；环境没有该依赖时采用保守字符估算。正式实验的 `config_hash` 会记录实际配置，防止结果混淆。

## 3. 评测方法

命令：

```powershell
python scripts/run_chunking_benchmark.py
```

评测输入为 `zh_public_minibench_v0.1`：55 个数据条目、55 个问题。由于两对 Markdown 文件内容和 SHA-256 完全相同，统一文档 ID 去重后实际是 53 份唯一文档：

- `tableeval-0007` 与 `tableeval-2043`；
- `tableeval-0002` 与 `tableeval-2040`。

缺少的 Markdown 解析结果会由本地解析器补入正式评测命名空间。输出位置：

```text
storage/evaluations/zh_public_minibench_v0.1/
├── parsed/<document_id>/parsed_document.json
├── chunks/<strategy>/<document_id>/chunks.jsonl
└── reports/node4_chunking*.json
```

这些是可重建的大体积运行工件，受 `.gitignore` 管理，不提交 Git；实现代码、测试和本文档提交 Git。

### 3.1 指标含义

- `evidence_preservation_rate`：把相关文档的块重新合并后，金标证据是否仍被保留；
- `single_chunk_evidence_coverage`：单个块能否覆盖金标证据；长于上限的整页金标不会被错误地当作“必须塞进一个块”；
- `answer_coverage`：相关文档的块中是否仍包含标准答案表达；
- `traceable_chunk_rate`：块是否同时具有元素 ID 和原文位置；
- `oversize_chunk_count`：是否违反最大 Token 硬限制；
- 短块率、精确重复率和块数：用于估算噪声、存储和向量化成本。

这里的证据/答案覆盖是切块阶段的静态检查，不等同于模型能够召回这些块。

## 5. 当前决策

节点 5 默认使用：

```text
strategy = structure_aware_v1
target_tokens = 600
max_tokens = 800
overlap_tokens = 80
table_rows_per_chunk = 20
```

理由：

1. 在真实 `cl100k_base` tokenizer 下，600/800 的答案覆盖率高于另外两组，综合分最高；
2. 2,881 个块全部具备原文证据映射，能够支持引用、问题定位和未来前端预览；
3. 没有超限块，平均 454.47 Token、P95 为 754，在上下文完整度和成本之间较平衡；
4. 固定 Token 仍作为强基线保留。它的单块证据覆盖更高，若节点 5 的真实 Recall@K 明显胜出，就应回到数据重新判断，而不是为了“结构更先进”强行采用结构方案。

结构感知方案的静态证据保留率低于固定 Token，主要失败集中在超长整页金标、复杂 Excel 和重复视觉文本。这一差异已经记录，节点 5 必须通过真实召回实验验证，不能被综合分掩盖。

## 6. 自动化验证

`test/test_chunking.py` 覆盖：

- 配置边界和非法参数；
- 标题路径、元素 ID 与来源位置；
- 表头重复、表格分片和公式保留；
- 超长无标点文本的 Token 硬上限；
- 稳定 Chunk ID；
- 原法律策略仍可注册、构建和自动推荐。

## 7. 已记录但暂缓的前端能力

Chroma/Qdrant 对比完成后，Streamlit 增加切块预览：

- 用户选择策略；
- 设置目标 Token、最大 Token、overlap 和表格行数；
- 同屏查看块边界、Token、标题路径和原文位置；
- 预览配置可直接用于正式入库；
- 正式入库保存相同的配置和 `config_hash`，保证预览与结果一致。

本节点已经提供上述界面所需的策略注册表、配置模型和统一输出，不提前制作界面。

## 8. 下一节点

固定 `structure_aware_v1 / 600 / 800 / 80` 作为主实验输入，同时保留 `fixed_token_v1 / 600 / 800 / 80` 作为切块基线，开始 Chroma 与 Qdrant 的公平对比。数据库实验至少输出 Recall@K、MRR、nDCG、完整证据召回率、延迟、索引体积和部署复杂度，最终形成是否迁移的决策记录。
