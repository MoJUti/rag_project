# 节点 6：混合召回与重排（进行中）

## 目标与当前进度

在固定的中文文档、结构感知切块和2048维向量上，比较检索方式，随后接入可切换的融合与重排策略。当前完成了正式Chroma集合上的基线、中文词法探索与千问重排离线评测；2026-10-14已把可选重排和阶段追踪接入问答检索路径，默认重排关闭，节点尚未验收。

## 基线如何运行

`scripts/run_node6_retrieval_baseline.py`使用55个已标注问题、53份文档的2,881个切块和已有问题向量缓存运行三组检索，不调用嵌入API：

| 方案 | 实际路径 |
|---|---|
| 仅向量 | 当前Chroma集合，返回前10条 |
| 仅BM25 | 当前字符级分词实现，返回前10条 |
| 当前混合 | 向量前20 + BM25前20，RRF常数60，评测前10条 |

应用实际交给生成模型的是前6条，因此同时报告 `@6`。评测沿用已有标注、证据引文匹配和指标函数；结果保存为本地JSON，运行文件不提交Git。

```powershell

```

## 第一轮结果

下表来自修正重复读取后的同一次运行；延迟为本地、单线程、已建好BM25索引的查询时间，不代表并发服务性能。

| 指标 | 仅向量 | 仅BM25 | 当前混合RRF |
|---|---:|---:|---:|
| MRR，越高越好 | 0.973 | 0.750 | 0.939 |
| 文档Recall@6 | 96.36% | 86.36% | 95.45% |
| 证据Recall@6 | 70.61% | 56.06% | 69.70% |
| 完整证据命中@6 | 67.27% | 54.55% | 67.27% |
| 文档Recall@10 | 98.18% | 90.00% | 97.27% |
| 查询P50 | 3.45 ms | 18.39 ms | 23.01 ms |
| 查询P95 | 4.78 ms | 31.33 ms | 33.09 ms |

当前问题集上，字符级BM25单独使用明显弱于向量；未经调优的RRF在前6条没有稳定改善证据召回，也降低了首个相关结果的排序。一次运行不能证明向量策略对所有用户文档都更优：先前一次运行的向量Recall@10为96.36%，混合为97.27%；这次向量为98.18%，混合为97.27%，说明近似向量索引的排名存在波动。接下来需要重复运行、分问题类型分析，并用独立验收集验证调参结论。

按模态初步查看，37道普通文本题的证据Recall@6分别为：向量66.2%、BM25 54.1%、混合64.9%；9道结构化Markdown题为向量92.6%、BM25 59.3%、混合92.6%。图片OCR题只有7道、跨文档题只有2道，样本太少，不能据此选择专门策略。

发现当前混合检索每次提问都从Chroma读取全部2,881条文档，即使BM25索引没有变化。加入数量检查后，条数不变便复用已建索引；同一轮测试里混合P50从约246 ms降至23 ms。**限制：若切块内容替换但总数不变，现有缓存不会自动失效**；正式上传/删除流程接入前，需要引入索引版本或显式失效通知。融合去重优先使用稳定的 `chunk_id`，避免依赖进程内随机哈希。

## 第二轮：中文词法与融合参数（离线探索）

运行 `scripts/run_node6_fusion_experiment.py`。两种BM25词元：原有单字；汉字单字+相邻双字、英文/数字整体。融合固定RRF常数60，分别试10/20/40候选及BM25权重0.25/0.5/1/2。所有方案在**同一次运行**共享向量候选，避免把近似索引的运行间波动误认为参数收益。`dev`与`smoke`共34题只用于探索，`holdout-public`为21题，单独汇报。

| 方案 | 开发题证据Recall@6 | 保留题证据Recall@6 | 开发题文档Recall@6 | 保留题文档Recall@6 |
|---|---:|---:|---:|---:|
| 仅向量 | 83.82% | 49.21% | 94.12% | 100.00% |
| 原有单字BM25 | 66.18% | 39.68% | 80.88% | 95.24% |
| 单字+双字/英文数字整体BM25 | 82.35% | 50.79% | 98.53% | 100.00% |
| 原有混合：单字BM25、两路各20、等权 | 82.35% | 49.21% | 92.65% | 100.00% |
| 探索方案：改进BM25、两路各10、等权 | 83.82% | 55.56% | 98.53% | 100.00% |

改进词元使BM25本身明显改善，证明当前单字处理是瓶颈之一。但最佳开发题证据召回来自“原有词元、40候选、BM25权重0.25”（85.29%），在保留题只有50.79%；改进BM25的10候选等权方案开发题没有超过仅向量，保留题却达到55.56%。这不是稳定的统一赢家。且21道保留题的结果已被查看，今后不能再把它称为完全未见数据做最终验收。当前仅保存探索代码及报告，不修改线上默认词元、权重或候选数量。

这一轮只评测检索质量，没有测改进词元后的建索引内存、耗时、查询延迟或真实问答质量。最终预设还需要新增盲测问题/用户文档，重复运行，比较完整答案与引用，再决定是否默认启用。报告保存于 `storage/evaluations/zh_public_minibench_v0.1/reports/node6_fusion_experiment.json`，本地报告不入Git。

## 可插拔检索管线落地（2026-10-14）

`retrieval/pipeline.py`统一组合查询处理、候选召回、融合、重排和证据扩展。`HybridRetrieverService.get_candidates()`提供候选池，`RagService.retrieve_with_trace()`供问答和后续预览共用。开启重排时先取最多40条候选并排序，然后才截断为6条，避免在重排前丢掉候选。混合候选最多来自向量20条与BM25 20条的去重集合，不会为凑够40条扩大两路配置。

`retrieval/tokenizers.py`抽取已经评测过的词元实现，让实验与正式检索共用。以下配置可放入本地 `.env`；修改后重启应用加载：

```dotenv
RETRIEVAL_STRATEGY=hybrid_rrf
BM25_TOKENIZER=mixed
RERANK_STRATEGY=qwen3.7-text-rerank
RERANK_CANDIDATE_K=40
```

这组是已评测的实验配置，尚未成为全局默认；默认词元仍为 `char`，重排为 `none`。仅向量、仅BM25、混合召回均可配合可选重排。开启重排会按问题调用外部排序API，模型故障明确报出重排阶段及HTTP错误，不默默换成另一条结果。客户端在每次调用后关闭；空候选不调用模型。

每次运行返回 `documents` 和 `trace`。追踪包含阶段耗时、问题列表、排序前后稳定块ID、重排Token和请求ID，可直接用于界面解释。查询改写、父块扩展目前只提供插件接入点，更多算法及验收顺序见[检索策略扩展计划](检索策略扩展计划.md)。

补充了BM25显式失效入口 `invalidate()`，用于同数量切块替换；未来上传/更新流程需要在写入后调用。当前数量检查仍无法感知其他进程的同数量更新。核心测试覆盖重排前候选预算、最终截断、来源保留、空结果、多个问题融合、无效配置、失败后的客户端关闭及缓存失效。

本次验证：69项自动化测试通过。另用正式库2,881个切块及缓存问题向量，比较两种词元×三种召回方式×55题，共330次关闭重排的本地对照；新管线结果与直接调用原检索服务一致。这轮验证没有调用模型API。重排接入使用替身测试候选预算及来源保留，真实模型效果依据前面的55题实测；尚未运行完整生成模型问答。
